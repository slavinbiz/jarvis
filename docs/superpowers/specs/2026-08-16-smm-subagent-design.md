# SMM-субагент для канала @santex_s_ai — дизайн

Дата: 2026-08-16
Статус: одобрено Вячеславом, ждёт написания implementation-плана

## Контекст

Сейчас черновики постов для @santex_s_ai пишет сам Jarvis (я), используя скилл
`santex-post-writer` внутри своей же сессии — по расписанию из напоминаний
(`reminder`), с ручным согласованием у Вячеслава перед публикацией.

Вячеслав хочет ролевую модель «сотрудник»: отдельный субагент-специалист,
которому делегируется задача по ТГ-каналу и от которого приходит отчёт —
первый из потенциальной линейки подчинённых агентов (по аналогии с
заготовками `SOUL-coder.md` / `SOUL-researcher.md` / `SOUL-strategist.md`,
но реализованный через официальный механизм именованных субагентов, а не
через переключение личности внутри одной сессии).

## Мотивация (из брейнсторминга)

- Основной драйвер — ролевая модель «сотрудник», не изоляция памяти и не
  расширение обязанностей за пределы канала (комментарии/метрики — не в
  скоупе на старте).
- Ответственность на старте: черновики постов (все 3 типа по контент-плану)
  + самостоятельное отслеживание расписания публикаций — без участия
  Вячеслава или меня в качестве «напоминалки».

## Архитектура

### Компонент 1 — `.claude/agents/smm.md`

Новый именованный субагент, вызываемый через `Agent` tool как
`subagent_type: "smm"`. Это правильный механизм для модели «делегировал
задачу — получил отчёт»: frontmatter (name, description, tools, model) +
системный промпт-персона.

- Персона: SMM-сотрудник канала @santex_s_ai, знает контент-план, голос
  канала, ограничения (никогда не упоминать VPN-бот и т.д.)
- Правила стиля/формата не дублируются — либо инлайнятся в тело агента,
  либо агент первым действием грузит скилл `santex-post-writer` (решается
  на этапе implementation-плана, не принципиально для дизайна)
- Отдельной памяти/контекста агенту не выделяется — работает на общем
  `MEMORY.md`/`knowledge/`, как и остальная система. Причина: юзер явно не
  выбрал «изоляцию памяти» как мотивацию при брейнсторминге.

### Компонент 2 — триггер через существующий планировщик бота

Расписание живёт в `schedules.json` бота (`bot/index.js`,
`startScheduler`/`loadSchedules`) — тот же механизм, что сейчас шлёт
Вячеславу напоминания. Меняется формулировка задачи в расписании: вместо
«напомни мне про пост» — «сегодня день подготовки [тип поста], задиспетчери
SMM-агента».

Следствие: функциональность исполняется на инстансе Jarvis-бота на Fornex
(там, где идёт живая переписка с Вячеславом в Telegram), а не обязательно в
локальной сессии на компьютере. Определение субагента (`.claude/agents/smm.md`)
и правки `schedules.json`/скрипта планировщика — в общем git-репозитории,
поэтому доступны из любой сессии Jarvis.

## Матрица прав публикации

| Тип поста | День | Публикация |
|---|---|---|
| Дайджест новостей ИИ | суббота | Публикует SMM-поток сам, без согласования |
| Пост о продаже продукта | по ситуации | Черновик → Вячеславу на "ок" → публикация после подтверждения |
| Пост про практику | вторник/четверг | **Открытый вопрос.** Пока — как продажа (безопасный дефолт, черновик на согласование). Пересмотреть после того, как автопубликация дайджестов пройдёт проверку на практике |

Технический канал публикации не меняется: Bot API через `@dgarvise_bot`
(бот уже админ канала), как и сейчас.

## Поток выполнения (пример: дайджест)

1. Планировщик бота триггерит в пятницу: «готовь субботний дайджест»
2. Главная сессия Jarvis (на Fornex) вызывает
   `Agent(subagent_type: "smm", ...)` с задачей
3. SMM-субагент собирает новости, пишет черновик в голосе канала, при
   необходимости — генерирует картинку (Pollinations.ai, как сейчас)
4. Возвращает отчёт главной сессии (репорты субагентов не показываются
   пользователю напрямую — их всегда релеит вызвавшая сессия)
5. Т.к. тип поста — дайджест: главная сессия публикует через `@dgarvise_bot`
   сама, без ожидания "ок", и присылает Вячеславу в Telegram уже факт
   публикации + текст поста

Для «продажи» и (пока) «практики» шаг 5 меняется: черновик уходит
Вячеславу, публикация — только после явного подтверждения.

## Обработка ошибок

Если сбор новостей, генерация картинки или сам субагент завершились
неудачно — ничего не публикуется вслепую. Главная сессия сообщает
Вячеславу, что именно не получилось, и не берёт на себя решение
«опубликовать как есть».

## Что осталось прежним (не меняем)

- Голос и форматирование канала — правила `santex-post-writer` (HTML для
  Telegram, жирный только в заголовке, без markdown и т.д.)
- Жёсткое ограничение: никогда не упоминать VPN-бот `@djarvisvpn_bot`
- Технический канал публикации — Bot API, `@dgarvise_bot`

## Не в скоупе на старте

- Отслеживание метрик канала
- Отдельная память/контекст для SMM-агента
- Второй Telegram-бот или отдельный канал связи с Вячеславом — вся связь
